Isolated .NET SDK

Install. Use. Verify. Remove.

Manage exact .NET SDK versions in a user-owned directory without changing system-wide installations or PATH. Supported through PowerShell on Windows and Bash on Linux/macOS.

View source code ↗Read documentation ↗
01 / Why

The problem

Different projects can require exact .NET SDK versions without changing the SDK configuration of an entire machine. Evaluating prerelease SDKs or reproducing a version-specific issue should not disrupt a predictable daily development environment.

A repeatable workflow needs more than a one-time installation: developers also need to understand which SDKs are available, whether an installation is healthy, and how to remove it safely.

02 / What

The solution

Isolated .NET SDK manages selected versions under a user-owned directory, keeping system-wide SDKs and PATH untouched. Installation, listing, auditing, verification, and removal are distinct operations.

Exact version selectionInstall specific SDK versions deliberately rather than relying on ambient machine configuration.
Independent inventoryList and audit isolated installations without changing the system's installed SDKs.
Controlled removalRemove SDK versions managed under the isolated directory when they're no longer needed.
03 / Who

Who it's for

Developers and CI maintainers who want predictable SDK versions without modifying machine-wide configuration. Typical uses include trying a new release, reproducing a version-specific issue, and running an SDK outside a team's normal setup.

04 / How

How it works

01
Install a selected SDK

Stage an exact SDK version under the isolated root, verify checksum and version information, then promote it into the managed inventory.

02
Inspect, audit, and verify

Separate operations make the installed inventory, servicing status, and installation health visible.

03
Use it explicitly, then remove it

Invoke the chosen isolated SDK directly without switching PATH. Remove versions that are no longer required.

05 / Engineering perspective

Design decisions that matter

  • Isolation over global changes. Managed SDK files stay in a user-owned location and do not replace the machine's default configuration.
  • Verification over assumption. Version and integrity checks are part of the installation workflow.
  • Explicit platform interfaces. PowerShell is supported on Windows; Bash is supported on Linux and macOS.
  • Clear security boundaries. Filesystem isolation is not a security sandbox; SDK processes still run with the current user's permissions.

Explore the implementation

Installation, auditing, verification, and removal are documented. The repository and published documentation provide current commands, prerequisites, and limitations.
